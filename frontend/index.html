S

Shared lock

Taken by reads. Many transactions may hold S on the same item at once.

X

Exclusive lock

Taken by writes, inserts and deletes. Nobody else may hold any lock on that item.

2PL

Two-phase locking

Acquire locks while growing, then release them while shrinking. Never acquire after releasing.

DL

Deadlock

A cycle in the wait-for graph. The DBMS aborts one victim so the others can continue.

State transition rules

The only transitions the DBMS allows. Every arrow on the lifecycle map is one of these.

01

NEW → ACTIVE

A newly created transaction begins execution.

02

ACTIVE → PARTIALLY COMMITTED

The final statement has executed successfully, but the commit is not yet durable.

03

PARTIALLY COMMITTED → COMMITTED

The commit record is written to stable storage and the changes become permanent.

04

COMMITTED → TERMINATED

The completed transaction leaves the system and releases its locks.

05

ACTIVE → FAILED

An error, deadlock, crash, or other condition prevents normal execution.

06

PARTIALLY COMMITTED → FAILED

A failure occurs before the commit became durable, so the transaction cannot commit.

07

FAILED → ABORTED

The DBMS rolls back the transaction using the log and restores consistency.

08

ABORTED → TERMINATED

Resources are released; the transaction may later be restarted or killed.

ACID properties

Why transaction management is essential for reliable databases.

A

Atomicity

A transaction is treated as one unit. Either all required operations succeed, or the DBMS rolls them back.

Seen in: FAILED → ABORTED
C

Consistency

A successful transaction takes the database from one valid state to another valid state.

Seen in: COMMITTED
I

Isolation

Concurrent transactions should behave as if their conflicting operations were appropriately controlled.

Seen in: isolation level setting
D

Durability

Once a transaction commits, its changes survive subsequent failures.

Seen in: PARTIALLY COMMITTED → COMMITTED

How to demonstrate the project

  1. Choose a transaction operation and isolation level.
  2. Press Start to watch the successful lifecycle.
  3. Use Next state (or Space) to explain each DBMS state manually.
  4. Select Failure & rollback or press Inject failure before the commit.
  5. Observe FAILED → ABORTED and the operation rollback.
  6. Hover any state on the map for a short explanation.
  7. Press AI explain for a per-state explanation, or open Ask AI to ask anything.
  8. Export a PDF/JSON report, and use Timeline, Transition rules, ACID properties and History from the sidebar during your viva.
The backend persists every run to SQLite and powers AI explain, Ask AI and report export. Without it, the simulator still runs locally in offline mode.
