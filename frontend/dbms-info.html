DATABASE MANAGEMENT SYSTEMS

Transactions & Concurrency Control

A detailed guide to how database systems execute, isolate, synchronize, commit, rollback and recover transactions.

01

What is a Transaction?

A transaction is a logical unit of database work consisting of one or more operations. A transaction normally contains read and write operations and eventually reaches either COMMIT or ROLLBACK.

READ

Retrieves data from the database.

WRITE

Modifies database data.

COMMIT

Permanently makes successful changes durable.

ROLLBACK

Undoes changes made by a failed transaction.

Example — Bank Transfer 
T1:
    READ(A)
    A = A - 100
    WRITE(A)

    READ(B)
    B = B + 100
    WRITE(B)

    COMMIT

A transfer should behave as one logical operation. If the transaction fails after deducting money from A but before crediting B, the database must be able to undo the partial work.

NEW

The transaction has been created but execution has not started.

The transaction is executing its read/write operations.

The final statement has executed, but the commit is not yet guaranteed durable.

The transaction has successfully completed and its effects are durable.

FAILED

An error or system condition prevents normal completion.

ABORTED

The transaction has been rolled back.

03

ACID Properties

ACID describes the fundamental guarantees expected from reliable transaction processing.

A

Atomicity

A transaction is treated as one indivisible unit. Either all required operations succeed or the database rolls back the transaction's effects.

C

Consistency

A successful transaction preserves database constraints and moves the database from one valid state to another.

I

Isolation

Concurrent transactions should not expose intermediate states in ways that violate the selected isolation model.

D

Durability

After successful commit, the effects of the transaction must survive subsequent failures.

04

Schedules

A schedule represents the order in which operations from multiple transactions are executed.

Serial Schedule

T1: R(A) W(A) COMMIT
T2:              R(B) W(B) COMMIT

T1 completes before T2 starts. There is no interleaving.

Non-Serial Schedule

T1: R(A)       W(A)
T2:       R(A)       W(B)
T1:                    COMMIT
T2:                         COMMIT

Operations from multiple transactions are interleaved. This improves concurrency but introduces consistency concerns.

05

Serializability

Serializability is a correctness criterion for concurrent schedules. A concurrent schedule is serializable when its effect is equivalent to an appropriate serial execution.

Conflict Operations

Two operations conflict when they belong to different transactions, access the same data item, and at least one operation is a write.

Operation 1 Operation 2 Conflict?
R1(A) R2(A) No
R1(A) W2(A) Yes
W1(A) R2(A) Yes
W1(A) W2(A) Yes

06

Concurrency Problems

Dirty Read

T2 reads a value written by T1 before T1 commits. If T1 subsequently rolls back, T2 has read data that never became part of the committed database state. 

                  T1: WRITE(A = 500)
                  T2: READ(A = 500)
                  T1: ROLLBACK

Non-Repeatable Read

A transaction reads the same row twice and obtains different committed values because another transaction modified the row between the two reads.

Phantom Read

A transaction executes the same predicate query twice and the second execution returns additional or missing rows because another transaction inserted or deleted qualifying rows.

Lost Update

Two transactions read the same value and subsequently write based on that stale value. One update can overwrite the other's result.

08

Locking & Two-Phase Locking

Locks coordinate concurrent access to shared database resources. A DBMS can use locks to prevent destructive interactions between transactions. :contentReference[oaicite:3]{index=3}

Shared Lock — S

Used for reading. Multiple transactions can generally hold compatible shared locks on the same resource.

Exclusive Lock — X

Used when a transaction needs to modify a resource. Conflicting transactions must wait or otherwise be prevented from accessing the resource according to the locking protocol.

Two-Phase Locking — 2PL

PHASE 1 Growing Phase

Locks may be acquired, but not released.

PHASE 2 Shrinking Phase

Locks may be released, but new locks cannot be acquired.

Strict variants of locking protocols impose additional restrictions on when write locks can be released, which helps simplify recovery and prevents certain cascading effects.

10

Transaction Recovery

Recovery mechanisms restore the database to a consistent state after transaction failures, system crashes or other interruptions.

FAILURE
→
DETECT
→
UNDO / REDO
→
CONSISTENT STATE

Log-Based Recovery

A recovery log records information that allows the system to reconstruct or reverse database changes.

UNDO

Reverses effects of transactions that should not remain in the database.

REDO

Reapplies effects that should be reflected in the durable database state.

Write-Ahead Logging

Write-ahead logging requires the relevant log record to be written to stable storage before the corresponding database change is treated as safely persisted.

Checkpoint

A checkpoint records a recovery point so that recovery does not necessarily have to process the entire history of the database log.

11

Recoverability

Recoverable Schedule

A transaction that reads data written by another transaction does not commit before the transaction it depends on commits.

Cascading Rollback

A transaction failure causes other transactions that consumed its uncommitted data to roll back.

Cascadeless Schedule

Transactions only read data written by transactions that have already committed.

Strict Schedule

Data written by a transaction cannot be read or overwritten by another transaction until the first transaction commits or aborts.
